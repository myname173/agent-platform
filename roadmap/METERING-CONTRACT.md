## 1. 什么算一次成本

- **单位**：USD，`cost_usd` 精度 6 位小数；`cost_usd = Σ(token_count × unit_price) / 1000`，三类 token（输入 / 输出 / 缓存命中）分别取单价。
- **「一次成本」= 一次按 token 计费的上游调用尝试（attempt）** —— 当前即模型推理调用。成本公式按 token 与单价计算，因此**本口径现阶段限定为 token 计费的上游调用**；非 token 计费的外部 API / 按次计费服务**暂不纳入**，等出现实际用例再扩展。纯内部、无外部成本的工具调用（读本地表、内存计算、内部状态查询等）同样不算一笔。按实际发生的调用计，**不按用户任务合并**。
- 工具循环内每次**按 token 计费的**上游调用各自计；任务级成本 = 其下所有 attempt 之和（工具循环轮数不固定，不能按任务拍一个数）。
- `cost_usd` 是**派生结果，不是必填输入**；遥测或牌价不全时允许为空，语义见 §5。

## 2. 失败重试怎么算

- **失败尝试计入 COGS**。a16z《Can Agents Use a Computer Yet?》一手：COGS = 推理 + 重试，**失败仍烧 token**。
- 同一任务的多次尝试分别记，不合并、不覆盖；取消 / 超时只要已产生上游调用，同样计入。
- 重试不产生新的 billable task，但产生新的成本。
- **重复投递不重复计费**是结果要求；**用什么键、什么存储去重，属于后续实现决策**（§7），本阶段不定。

## 3. 评测流量如何排除

- eval 流量带 `client = 'eval'`（网关既有 `x-client` 标记）；**业务成本与业务统计必须排除 eval 流量**，否则日报与账单会被评测跑批污染。
- `n8n/workflows/chat-stats-api.json:128` 的 `Build Stats` **源码已有** `const bizRows = rows.filter(... !== 'eval')`，缺的是部署不是补代码（F3）。
- 排除的是**业务口径**：评测自身成本仍应单独可查，不混进业务成本，也不从总量里悄悄删掉。

## 4. 牌价以什么为准

- **当前唯一权威**：`n8n/workflows/chat-gateway.json:248`（`Prep Success Log` 的 `PRICING`）；牌价变更今天仍需改 workflow（`README.md:1008`）。C0 **不改这处计算**。
- 口径要求：每次成本记录关联一个价目版本标识（含 `effective_from`）；牌价变更 = 新增版本，**不回写历史事件**，保证批次可比。
- 牌价缺失 / 无法解析时，该次成本记为「未知」，**不得估算、不得按 0 计**。

## 5. `cost_usd` 与遥测缺失（字段语义统一）

上一版把 `cost_usd` 标成必填、又要求遥测缺失时标成本未知，二者冲突。统一为：

| `cost_status` | `cost_usd` | 含义 | 是否计入聚合 |
| --- | --- | --- | --- |
| `known` | 数值（USD，6 位） | token 遥测完整且牌价可解析 | 计入 |
| `missing_telemetry` | `null` | 缺 token 遥测 | **不计入**，也不算 0 |
| `pricing_unavailable` | `null` | 牌价缺失 / 无法解析 | **不计入**，也不算 0 |

- 报告必须能区分「成本 0」与「成本未知」；`unknown` 不进聚合分子、也不进均值分母。
- **任务总成本完整性**：若一个成功任务中任一 attempt 的 `cost_status` 不是 `known`，该任务的**总成本视为不完整（incomplete）**，不得当作完整账单或对客报价依据；只汇总已知部分也不得标为「任务成本」。
- **覆盖率口径固定**：报告平均成本（北极星「每成功任务成本」）时，覆盖率为 **成本完整的成功任务数 ÷ 成功任务总数**。`known` attempt 数 / 总 attempt 数**只作诊断数据**，用于定位遥测缺口，**不与任务级指标混用、不替代该覆盖率**。
- 成本遥测缺失时评测跑批停止（`eval-run.mjs` 既有「Missing cost telemetry stops the run」），口径与此一致。
