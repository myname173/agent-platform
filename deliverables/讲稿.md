### 第 3 页 · 架构全景 · `02:30 – 04:00` ⏱ 90 s

**画面**:三层结构图。入口 → 编排核心 → 五类后端服务。

**台词**
> 一句话描述架构:四个入口、**一个主干**、五类后端。
>
> 入口有四个:Telegram、LobeChat、控制台、MCP。**重要的是它们后面只有一条主干**——同一个 Chat Gateway。意思是:换入口不换后端,工具、知识库、记忆、审批都是同一份。
>
> 这个 Chat Gateway 在 n8n 里,有 22 个节点,每次请求向模型注入 **15 个服务端工具**。模型自己挑用哪些,网关负责执行、回灌结果、控制最多 2 轮 —— 轮数是成本护栏,用完会强制模型说"信息不足",**不允许猜**。
>
> 五类后端是干活的:模型(DeepSeek + 通义做兜底)、检索(pgvector 加千问嵌入)、搜索(自建 SearXNG)、存储(Postgres 加 MinIO)、沙箱(代码审批放行)。

# Q&A · 10 个尖锐问题应答

## Q1:为什么不用 Coze / Dify / 智谱 / 扣子?

> **A**:三个理由。
> ① **数据要可控**。我的笔记、客户答疑、内部决策记录都不出机器。市面上的产品是 SaaS,即便有"我也部署"也是别人写的代码,我不能改。
> ② **要能改**。我的工具清单是动态的,要能加 MCP、调参数、改语义。市面产品都给你一个固定的工作流编辑器,改模型调用细节很难。
> ③ **要可证**。我要能查到"这条晨报是哪次 LLM 调用生成的、用了哪个工具、打了什么 prompt"。这两个问题我可以一行 SQL 查到,别人的产品不行。
> 简单说:不是技术不能做,是产品理念不同 —— 我要的是"我能改系统",不是"我用平台"。

## Q2:为什么用 n8n 而不是直接写 Python?

> **A**:n8n 在三个维度上省事:① **可视化编辑**,我和另一个开发者能直接对着图讨论"这个节点是干嘛的",不用读代码;② **webhook/trigger/定时任务** 不用自己造轮子;③ **重试、错误分支、限流** 是开箱即用的。
> 但 n8n 不是银弹。**真正决定性的逻辑(鉴权、工具编排、prompt 拼装)我都写在了 n8n 的 Code 节点里**,而不是用 n8n 的连线。我用 n8n 是用它的"骨架",不是用它的"血肉"。

## Q3:这套系统能不能平移到公司用?

> **A**:能,但要做四件事:
> ① **模型选型**:换公司允许的模型,可能要加合规审计
> ② **密钥管理**:`.env` 里的密钥换成 Vault,或者用 KMS
> ③ **权限模型**:现在是单租户单人,公司需要多用户多角色
> ④ **审计日志**:`admin_audit` 表需要外推到 SIEM
> 除此之外,**架构几乎不用动**。核心设计("一条主干 + 工具清单 + 流式")是平台无关的。

## Q4:每天跑大概要多少模型额度?

> **A**:我来报真实数字。过去 30 天,**累计 API 花费是 12 USD**(完整数据在 ops_alerts 表里)。主要花在 ① 晨报(每天一次);② 知识库嵌入(累计 83K token,大部分是一次性);③ 实时对话(我每天大约 10-20 条)。
> **每条对话的 token 成本是 0.001-0.003 USD**。也就是说一天 1 元以内,够个人用了。
> 如果要加企业级工作流(比如每天 1000 条提醒),预算会到 100 USD/天,这是给预算审批准备的。

## Q5:如果 Telegram 被封了怎么办?

> **A**:**Telegram 不是系统的核心,只是入口之一**。
> 关键功能(晨报、提醒、自检、备份)都跑在 Docker 容器里,不依赖任何外部消息服务。
> Telegram 挂了,LobeChat、控制台、MCP 都能用。我也可以加飞书、企业微信、邮件、短信作为备用,**这是配置而不是代码改动** —— 我在 Telegram Bridge 旁边预留了 Feishu Bridge 的工作流槽位。

## Q6:你怎么保证知识库里的内容质量?

> **A**:四个机制:
> ① **来源标注**:每条都标 manual / chat / doc,chat 来源的内容我会回头审
> ② **归档状态**:已归档的文档不会出现在检索结果(默认 active)
> ③ **归档阈值**:超过 30 天未引用的会提示"是否还在用"
> ④ **检索打分面板**:在控制台里我能直接看"这段有没有人查过、查出来排第几",**不被引用的内容自然会被发现**
> 但坦白说,**没有自动化的质量保证**。这是个人系统,我对自己的要求是"每周扫一眼归档列表"。

## Q7:失败的时候你会知道?

> **A**:会,而且**会立刻告诉你**。
> - 错误率超过 50% → Telegram 立刻收到
> - 24h 成本超过 2 USD → 警告
> - 超过 5 USD → 加急升级
> - 自检失败 → 邮件 + 电报
> - 备份静默 → 守卫标记不写 → 下次启动时检查会告警
>
> 我**最恨**的不是失败,是"失败我不知道"。所以告警宁可多不可少,而且静音一定要留痕(delivered 字段会写 silenced:maintenance,而不是静默吞掉)。

## Q8:整套系统部署要多久?

> **A**:**从零到能跑,半天**。我自己搭了 5 天(其中 3 天在踩坑)。如果用我现有的脚本和知识库:
> - docker compose up(5 分钟)
> - 跑初始化脚本(2 分钟)
> - 接模型 API(5 分钟)
> - 配置人员目录(1 小时)
> - 配告警阈值(30 分钟)
>
> **真正耗时间的是配数据**。技术部分已经不是瓶颈,**怎么用才是**。

## Q9:你的代码多少行?

> **A**:核心目录(n8n/workflows + frontent/src/features + stream-bridge + backup)大概 **2 万行**。其中:
> - 60% 是 n8n 工作流 JSON(每个 workflow 平均 500 行)
> - 25% 是前端组件(Next.js + React)
> - 10% 是后端 API 路由
> - 5% 是脚本(测试、校验、采集)
>
> 我没有写测试覆盖率指标 —— 个人系统写覆盖率不划算,但**每个工作流都有端到端的健康检查**(就是 selfcheck 那个工作流)。

## Q10:如果模型厂商明天关门了呢?

> **A**:**不会立刻死**。
> - **模型接口是 OpenAI 兼容的**。换厂商只需要改 4 个环境变量(API key + base URL),代码不动。
> - **知识库、提醒、待办、记忆、审批**都不依赖模型,模型挂了这些还在。
> - **流式透传**也跟模型无关,它跑在 stream-bridge 侧车里。
>
> 真正受影响的只有"实时对话"。但是 24 小时内的对话有缓存(chat_messages),不会丢。
>
> **最坏情况**:模型挂 → 我用控制台人工调度 → 数据不丢 → 接上别家 → 自动恢复。**整套系统是为"长期可演化"设计的,不是为"用一辈子"设计的**。
