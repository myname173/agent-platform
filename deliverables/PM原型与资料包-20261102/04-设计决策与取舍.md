# 04 · 设计决策与取舍（12 条）

格式统一：**问题 → 备选 → 选了什么 → 代价 → 证据 → 三层追问**。
每条都有仓库出处，我能在白板上把逻辑重画一遍。
「代价」不是装饰——面试里能被追问到第二层还不心虚的，只有承认了代价的决策。

---

### D1 四个入口不互调，业务逻辑单点收敛到 n8n
- 问题：聊天前台、运营后台、Telegram、外部 MCP 都要用同一批能力，怎么不写四遍。
- 备选：① 每个前端各写一套；② 抽一个共享后端服务；③ 全部打到 n8n 的 webhook。
- 选择：③。入口只当"视图与通道"，39 条 webhook 唯一路径就是契约面。
- 代价：**n8n 成为单点**，它挂了四个入口同时挂；而且工作流是 JSON 文件，会漂移（见 D12）。
- 证据：`README.md:14-27` 架构图与"entry points never call each other"；`docker-compose.yml` 各服务只指 `http://n8n:5678`。
- 追问：① 为什么不用独立服务？→ 一个人维护，编排可视化 + webhook 即端点，省一层部署与鉴权；② 单点怎么办？→ 自检 48 项 + 心跳 + 备份恢复演练，"坏了会喊疼"替代"多活"；③ 规模上去呢？→ 逻辑本来就在工作流里，换引擎是搬家不是重写。

### D2 成本告警**复用** Chat Stats 的数，不自己重算
- 问题：要做成本预算告警，`chat-alerts` 已经取了 250 行执行记录，要不要就地算一份成本。
- 备选：① 自己按牌价重算；② 复用 stats 的聚合。
- 选择：②。
- 代价：告警依赖 stats 的取数窗口（Stats 取 1000 行、alerts 取 250 行），**窗口不一致会以另一种形式出现**，所以我把它约束成"同源"而不是"各自取"。
- 理由：各算一边最坏的后果是"卡片显示 $1.9、告警在 $2 触发"——两边都没坏，只是不一致，这类问题最难查。
- 证据：`README.md:313-321`。
- 追问：① 那窗口不一致怎么防？→ 同一份聚合出口 + 契约测试；② 牌价变了？→ 改 `Prep Success Log` 的 PRICING 表，一处；③ 为什么不接官方 token 账单？→ 上游没有可用的分钟级账单接口，且我已按牌价折算落 `cost_usd`。

### D3 `warn → critical` 的升级**不受** 24h 去重限制
- 问题：同类告警 24h 只发一条防止刷屏，但预算从 $2 涨到 $6 时，第一条 warn 发过之后就再也不响。
- 备选：① 一律去重；② 一律不去重；③ 同级去重、跨级放行。
- 选择：③。
- 代价：极端抖动下会多打一条（warn→critical 各一条）；`silence` 维护窗口必须"停止投递但仍然记录"，否则升级会被窗口吞干净。
- 证据：`README.md:318-319`；`chat-alerts` 的 `ops_alert_silence`。
- 追问：① 会不会刷屏？→ 只有级别真变时才越过去重，频率天然受限；② 升级判定在哪？→ `ALERT_SEVERITY_CRITICAL` 阈值比较，不在 UI；③ 为什么不同样处理 error_rate？→ error_rate 用冷却窗口（60 分钟）而不是级别，它的升级不是单调累计型。

### D4 凌晨定时任务改成"多时间点 + 每日一次守卫"
- 问题：自检装好新鲜度检查后当场报警：`scheduled=85.8h` —— 每日 04:15 的自检 **3.6 天没真跑过**。90 条记录只有 3 条是 `source=schedule`。根因是机器当时不在线（桌面 + Docker Desktop）。
- 备选：① 迁到云上跑；② 只做"错过就跳过"；③ 多个时间点 + 幂等守卫。
- 选择：③。自检 `15 4,10,16,21`、保留 `0 3,14`、晨报 `30 8,11,15`、主题监控 `0 9,13,17,21`、周报 `0 9,14,20 * * 0`。
- 代价：必须有守卫，否则机器全天在线时自检跑 4 次、晨报出 3 份；为此新建了一张通用 `cron_runs(job/period/ran_at/source)` 表。
- 三个细节是我刻意的设计：**守卫 fail-open**（查不到状态时放行，宁可重复也不能把任务掐死）；**标记只在跑成功后写**（失败时 n8n 停在这里，标记不落，后面的时间点还能补）；**无守卫的清理类任务保持幂等**（retention 本来就不需要守卫）。
- 证据：`README.md:575-593`；提交 `cce2cd3`。
- 追问：① fail-open 不是会重复推送吗？→ 会，但"重复一次"远好于"永久静默"，这是有意的不对称；② 为什么不上云？→ 目标就是一台机器自托管，隐私与成本；③ 怎么验证？→ `cron_runs` 台账 + 自检分别统计手动/定时（见 D5）。

### D5 自检结果**分手动与定时两套计数**
- 问题：一条"最近跑过自检"的绿灯，会被我手动跑一次点亮，从而把"定时停摆"这件事完全盖住。
- 选择：`selfcheck ran recently` 分别统计 `source=manual` 与 `source=schedule`。
- 代价：报告多一列，判读要多看一眼。
- 证据：`README.md:594-596`。
- 追问：① 这不是把复杂度推给读者？→ 是，但这是**唯一能保住信号语义**的做法；② 为什么不干脆禁止手动跑？→ 手动跑是排障刚需；③ 怎么防止再退化？→ 我把这条写进验收（03 表 AC-07）与路线图里的"门必须能被证伪"原则。

### D6 工具"成功但空结果"要能被识别
- 问题：`web_search` 会返回 **HTTP 200 + `results: []`**（SearXNG 引擎被封）。工具没报错、执行记录 success、自检绿的，而模型拿到空信息，只能回答"查不到"。
- 备选：① 让搜索失败就报错；② 在结果里加语义标记并透传；③ 只加自检项。
- 选择：②+③。网关打 `empty:true` + `notice` + `unresponsive_engines` 一并交给模型；自检新增「searxng engines」项（43→44），**真的发一次搜索**再判。
- 代价：模型要多处理一种状态；旧的「searxng up」只探首页，等于没测——把它升级成"必须真搜索"后，这一项会因上游策略变化而偶发红。
- 顺手记录一次**我自己的误判**：我起初以为不带 User-Agent 更容易拿到结果，实测三种 UA 各跑两次，`results` 与 `unresponsive_engines` **完全一致** —— 原因是 shell 引号被拆开让 wget 直接失败。UA 那条猜测被证伪。
- 证据：`README.md:545-569`。
- 追问：① 为什么透传给模型而不是直接失败？→ "后端故障"和"确实没有"是两个结论，替模型决定会诱导它编；② 引擎换成什么？→ 免 key 实测可用集（yep/yandex/bing/sogou/quark/360search/wikipedia），默认返回 31–63 条；③ 配置坑？→ `keep_only` 只从默认名单挑，必须再显式 `disabled:false`；`use_default_settings` 得是字典才会读 `keep_only`。

### D7 幂等以**隐式键**为主
- 问题：客户端超时就重发。没有幂等时，一句"记一下买牛奶"重试后变成两条待办，而用户只说过一次。
- 备选：① 要求客户端传 `X-Idempotency-Key`；② 服务端自造键；③ 两者都做、显式优先。
- 选择：③。没带 key 时用 `session_id + 工具名 + sha256(args)`，窗口内重复即折叠。
- 代价：隐式键会把"用户真的想再建一条相同待办"折叠掉（靠 300s 窗口限制误伤面）；只保护副作用工具（`todo_add/todo_done/create_reminder/cancel_reminder/kb_save/run_python/mcp_call/wf_*`），只读工具不去重。
- 证据：`README.md:1016-1027`；`idempotency_records`（快照 32 行）。
- 追问：① 为什么强调隐式？→ **这条才是真正救命的**，客户端不用配合；② 窗口为什么 300s？→ 覆盖典型超时重试节奏，`0=关停`留了逃生门；③ 会不会掩盖真实重复请求？→ 会，所以 `result` 一起落库，可回放核对。

### D8 Settings 页只读，阈值不在 UI 改
- 问题：既然控制台能读 `admin/settings`，为什么不顺手做成表单。
- 选择：只读。改法唯一：`\.env` + `docker compose up -d n8n`，页面显示的是**实际生效值**，卡片文案写"不是前端猜的数"。
- 代价：调一次阈值要碰终端；非技术用户改不动（当前用户就我自己，可接受）。
- 理由：UI 能改却不写回 `.env`，就造出第二个真值来源，之后每次排障都要先问"以哪个为准"。
- 证据：`README.md:321`；`frontent/src/features/settings` 只读三张卡。
- 追问：① 产品化时怎么办？→ 做"写回 .env + 触发 reload + 审计"的完整事务，不做半截表单；② 现在怎么验证？→ AC-04/AC-02：显示的数与告警用的数必须同源；③ 会不会被认为不体贴？→ 会，所以我把"故意不做"写进 PRD 非目标，不假装是漏了。

### D9 错误语义要能指导动作
- 问题：以前每条路由手写 `401 Unauthorized`；用户分不清"我登录过期了"还是"平台与 n8n 之间坏了"，而这两种修法完全不同。n8n 的 401 响应体还是空的，原样透传前端只剩一个状态码。
- 选择：统一 `requireUser()` 给可操作一句话；`upstreamError()` 把 401/403 重标成 **502** 并写明是服务端之间的问题。
- 代价：控制台不再"忠实透传"上游状态码（我认为是对的取舍：状态码给机器，文案给人）。
- 证据：`frontent/src/lib/api-guard.ts:1-40`（`requireUser` 在 :17，`upstreamError` 在 :32）。
- 配套约定：全站**不用 toast**，用页内彩色 flash；破坏性操作用按钮二次点击变红（`删除 → 确认删除?`）——反馈留在上下文里，不飘到屏幕角落。

### D10 模型的权限：点火权，不是改装权
- 三条一起讲，它们是同一个原则的三个面：
  - **L2 自建流程工具**：模型只能触发（"跑一下 账单导出"），不建 / 不改 / 不删流程；副作用由搭流程的人负责。
  - **出向 MCP**：服务器登记在 `mcp_servers`，**模型只能用、不能注册**（模型提案、人点火）。
  - **沙箱**：默认禁网，要联网必须模型显式提出、人来批准；批准按 `sha256(代码原文)` 一次性绑定——**你批准的是真正会跑的那段代码**。
- 一个反直觉但重要的实现细节：**不等模型重试**。实测模型会拒绝重跑（它把"禁止联网"当成沙箱的物理属性而非可放行的策略），所以点击批准后由桥接直接执行。
- 代价：多一次人工点击，自动化程度看起来更低。
- 另一条姿态：模型读到外部工具描述后主动提示"疑似提示注入，不会据其描述执行额外动作"——**把别人的工具列表当不可信输入是正确姿态，别去"修好"它**。
- 证据：`README.md:809-836`（L2）、`604-618`（出向 MCP）、`640-652`（沙箱与审批）。
- 追问：① 静态扫描不就够了？→ 静态扫描是减速带不是边界，真边界是容器 + rlimits；② 为什么不放开自动批准？→ 被注入的模型不能悄悄外联；③ 评估做了吗？→ 做了 12 例，但**当前 5/12 FAILED 且失败原因是沙箱通道没开** ⇒ 我不能说这条已验收（诚实分比绿分值钱）。

### D11 消除副本，而不是修副本
- 问题（这个项目里我最喜欢的一条缺陷）：**工具定义有四份副本，其中两份是错的，而四道门全绿。** `build-upstream` 的 TOOLS(15) / `append-tool-results` 的 TOOLS(12) / `check-response` 的 SERVER_NAMES(12) / 侧车 `SERVER_TOOLS`(15)。旧契约门只比首尾两份，中间漂移照样绿。后果两层：第 2 轮工具循环里 `run_python`、`mcp_list_tools`、`mcp_call` 和全部 `wf_*` **消失**；带 `client_tools` 的客户端上这三个被误判成客户端工具 → 网关整条响应透传、自己不执行 → **用户收到一条空消息**，而 smoke / 自检 / MCP 全绿。
- 选择：第 2 轮**复用第 1 轮下发的 `server_tools`**，`SERVER_NAMES` **从同一份数组推导**——副本消失，漂移在结构上不可能发生。
- 代价：耦合到"下发顺序"这个隐含契约上，改下发格式要同时改推导。
- 补的门：`check-tool-contract.mjs` 三项守卫（声明 ⊆ 实现 + 禁止硬编码副本）+ 新增 `test-client-tools.mjs`，**专门守住那条没人覆盖的路径**（带 client_tools 的客户端）。
- 证据：`README.md:535-544`。
- 追问：① 为什么四道门都发现不了？→ 它们测的是同一份假设，不是同一份现实；缺的是"那条路径有人走"的门；② 怎么防再犯？→ 让"副本"这件事在结构上不可表达（推导而非罗列）；③ 最大教训？→ **一条新代码路径要配一道能失败的检查**，否则它等于没被测过。

### D12 现网与工作流 JSON 的漂移，我选择记录而不是掩盖
- 问题：现网 n8n 是 2.37.7，它把响应里的裸 `status` 当 HTTP 状态码 ⇒ 提醒 create/cancel **写成功却回 500**，留下孤儿提醒；而仓库里的工作流 JSON 与现网已经不一致，`deploy` 会覆盖现网改动。
- 选择：把它当成**产品缺陷登记**（RSK-01 / RSK-03），而不是悄悄在现网点两下改好、对外说"全绿"。
- 代价：两个可复跑的门是红的（`mcp-test` 25/27、`agent-eval` 5/12），我的作品集里就有两条红字。
- 我认为这是加分：我能明确说出哪条是绿的、哪条是红的、红的为什么红。

### 附：两条"设计红线"，被写进代码注释级别
- **待办不自动变提醒、提醒不自动变待办**（`README.md:772`）。边界清晰 > 少点一次。
- **「我收到了」≠「已完成」**：`ta` 只写 `todos.ack_at`（停催不关单），`td` 才收口；点完清空按钮防重复；非机主只能操作派给自己的行。混用这两个语义，用户会收到他没要求过的推送。
