# 03 · 指标体系与验收标准

这份是我最愿意在面试里展开讲的一份：**它的主题不是"我有多少指标"，而是"怎么保证指标不是假的"。**

## 1. 指标只有五处来源，口径各不相同（混用就会出现同一个平台两个"总量"）

| # | 来源 | 位置 | 口径性质 | 引用时必须带的话 |
| --- | --- | --- | --- | --- |
| 1 | 侧车 Prometheus 文本 | `platform-runtime:13220/metrics`（28 series）、`stream-bridge:3211/metrics`（16 series） | 进程内计数器 | **随容器重启归零**，不能当历史累计 |
| 2 | 业务视图（控制台同源） | `admin/overview`、`webhook/v1/stats/executions` | 落库聚合 | 计数在 `totals` 下，不是顶层字段 |
| 3 | 五道门的分数 | `validate` / `smoke` / `mcp-test` / `agent-eval` / `selfcheck` | 可当场复跑 | 必须带 SKIP 状态（见第 4 节） |
| 4 | Data Table 台账 | `selfcheck_runs` `heartbeats` `cron_runs` `ops_alerts` `kb_usage` `daily_briefs` `idempotency_records` `sandbox_approvals` `tool_contract` | 历史累计 | rows API `limit ≤ 250`，超过报 400 ⇒ **给不出真实累计行数** |
| 5 | 一次性压测/评估记录 | `monitoring/*.md`（跑法也写在里面） | 有时间地点的实验 | 引用要带日期与当时并发档位 |

四个必踩的坑（每一个都会把"没取到"伪装成"没有"）：

- `?sortBy=createdAt:desc` 的**冒号必须百分号编码**，否则 400 而 `.data` 为空 ⇒ 我一度读成"这张表是空的"。
- rows API 不带 `sortBy` 时返回的是**主键最前面 N 行（最旧的）**；客户端再排序就是"在最旧的 N 条里挑最新"，实测把真实 0.1h 报成 30h。
- 侧车计数器随重启归零：10-30 那次 294/113 只是当天 10:30 UTC 之后这段窗口。
- **`stats` 的错误率只覆盖网关 `chat_executions`**，admin webhook 侧的 500 完全不计入 ⇒ "2.1% 错误率"与"提醒创建全挂"可以同时为真。

## 2. 北极星与护栏（分清"已有数据"和"我提议的口径"）

| 层级 | 指标 | 定义 | 现状 |
| --- | --- | --- | --- |
| 北极星 | **周内被真正闭环掉的 Agent 任务数** | 一轮对话触发副作用工具（`todo_add/todo_done/create_reminder/kb_save/run_python/mcp_call/wf_*`）且执行 `status=success`、且该副作用在 7 天内未被人工撤销 | **口径是我提议的**，数据源齐（`chat_executions` + `todos` + `admin_audit`），但没有现成聚合查询 |
| 质量护栏 | 网关错误率 | `stats/executions.totals.error / total`（窗口=累计，非 24h） | 已有。快照 2026-10-30：7/331 = **2.1%** |
| 成本护栏 | 24h 花费 / 预算 | 复用 Chat Stats 的 cost，不重算 | 已有。快照：24h `$0.009056`、7d `$0.113315`、累计 `$0.474466`，预算 $2 warn / $5 critical |
| 延迟护栏 | 首字延迟 / 端到端 p95 | 首字 1–3s 为流式验收；p95 取 `request_duration_ms` 分桶 | 首字已有体验基线；p95 有记录（`monitoring/baseline-2026-10-28`、`stability-load-2026-10-30`，2k/5k/10k @100/200/300 并发） |
| 检索护栏 | hit@5 / MRR | `kb-eval.mjs` 固定题集 | 已有：记录值 **1.0 / 0.903** |
| 自治护栏 | 自检通过率、备份新鲜度 | 48 项；心跳 >30h 警告、>40h 或不通过 ⇒ 判失败 | 已有 |
| 信任护栏 | **撞顶率**（跑满 `MAX_TOOL_ROUNDS` 的请求占比） | `cap-rate.mjs` | 已有记录（约 4–15%）；⚠ 配套的 `BUDGET_NOTE` 效果**未证实** |
| 安全护栏 | 注入题集通过率 / 沙箱审批率 | `agent-eval.mjs` 12 例（quality 2 / security 10） | **5/12 FAILED**：7 条失败全是沙箱通道没开；1 条是模型抖动 |

护栏指标的意义是**"涨到某个值就必须停下来解释"**，不是好看。所以每个护栏后面都接一条告警规则或一道门，见下表第 4 节。

## 3. 埋点 / 数据落点表（PM 视角：每个问题问得出、答得上）

| 事件 | 落点 | 关键字段 | 谁读它 |
| --- | --- | --- | --- |
| 一轮对话完成 | `chat_executions` | `client`、`model`、`status`、`latency`、`tokens`、`cost_usd`、`error_raw`(截断 2000) | 控制台 Operations / Overview、告警、成本 |
| 消息正文 | `chat_messages` | 会话 / 角色 / 内容，保留 30 天 | 统计去重、周报 |
| 副作用工具去重 | `idempotency_records` | `idem_key`、`tool_name`、`session_id`、`result`，保留 7 天 | 排障："为什么这条待办建了两遍" |
| 待办 / 提醒 / 人员 | `todos`、`reminders`、`people` | `status`、`due_date`、`due_at`、`ack_at`、`remind_count`、`escalated`、`attempts`、通道 | 派发闭环与升级阶梯 |
| 定时任务是否真跑 | `cron_runs` | `job`、`period`、`ran_at`、`source` | 每日/每周守卫；排"任务静默停了" |
| 自检结果 | `selfcheck_runs` | `report`(存 `{checks:[...]}`，不是裸数组)、`source` | 控制台历史；失败推 TG |

| 告警 | `ops_alerts`（+ `ops_alert_silence`） | `kind`、`severity`、`message`、`delivered` | Alerts 页、TG 投递 |
| 嵌入用量 | `kb_usage` | `total_embed_tokens` 累计 | 80% / 95% 两级告警 |
| 出向调用与越权 | `admin_audit` | `action`、客户端信息、参数摘要、耗时、结果 | MCP / L2 治理与事后追责 |
| 沙箱放行 | `sandbox_approvals` | 按 `sha256(代码原文)` 一次性绑定 | 安全评估题集 |
| 工具契约 | `tool_contract` | 声明 ⊆ 实现的守卫基线 | `check-tool-contract.mjs` |

## 4. 验收标准（Given-When-Then，每条都配一道**能失败**的检查）

写验收的规矩：**一条验收如果没有一个"把它做坏就会变红"的检查，它就不是验收，是愿望。**

| ID | Given | When | Then | 可证伪的检查 | 现值 |
| --- | --- | --- | --- | --- | --- |
| AC-01 | 同一 session 同一工具同一参数 | 客户端超时重发 | 不产生第二条副作用（显式 key 或隐式 `session+tool+sha256(args)` 折叠） | `smoke-test.mjs` 幂等组 | 71/71 通过 |
| AC-02 | 控制台显示 24h 成本 | 花费跨过 `$ALERT_COST_24H_USD` | 告警在**同一数值**上触发，不出现"卡片 $1.9、告警 $2" | 两边同源断言（cost 复用 stats，不重算） | 已实现 |
| AC-03 | 已发过 warn | 花费继续涨到 critical 阈值 | **必须再响一次**，不受同类 24h 去重限制 | 升级路径单测 | 已实现 |
| AC-04 | 用户会话有效但 `CHAT_API_KEY` 错 | 任意控制台请求 | 返回 502 + "n8n 拒绝了控制台的请求"，**不得**返回"登录已失效" | `console guards` 组 7 项 | 通过 |
| AC-05 | 网关下发的 `server_tools` | 第 2 轮工具循环 | 复用第 1 轮的数组；`SERVER_NAMES` 从同一份数组推导，**禁止硬编码副本** | `check-tool-contract.mjs`（三项守卫）+ `test-client-tools.mjs` | 通过；曾经的缺陷：四份副本、两份是错的、四道门全绿 |
| AC-06 | SearXNG 引擎被封 | `web_search` 返回 200 + `results: []` | 工具结果带 `empty:true` + `notice` + `unresponsive_engines` **透传给模型**，模型不得断言"不存在" | 自检里「searxng engines」**真的发一次搜索** | 通过（原「searxng up」只探首页，等于没测） |
| AC-07 | 机器凌晨不在线 | 到点多时间点任务 | 任一在线时点补跑，且**一天只真跑一次**；守卫 **fail-open**（查不到状态时放行） | `cron_runs` 台账 + 自检分别统计 `source=schedule/manual` | 通过 |
| AC-08 | 备份完成 | 心跳上报 | >30h 警告；>40h 或失败 ⇒ 自检判**不通过** | 自检数据新鲜度项 | 通过 |
| AC-09 | 摄取文档 | 出现超长分块 | 当日自检**失败**，而不是静默降低检索质量 | 自检分块守卫项 | 通过 |
| AC-10 | 模型要求联网 | 沙箱默认禁网 | 必须由人点击批准，批准绑定 `sha256(代码原文)`、一次性；**点击后由桥直接执行，不等模型重试** | `agent-eval.mjs` security 题集 | **5/12 FAILED**（沙箱通道未开）⇒ 这条现在是"未覆盖"，不能说已验收 |
| AC-11 | 负责人无投递通道 | 派发 | 回落机主 + `degraded`，正文追加"（注：X 没有可用通道，已改投机主）" | `notify` 工作流分支断言 | 通过 |
| AC-12 | 用户点「我收到了」 | 写回 | 只写 `todos.ack_at`（**停催不关单**）；「已完成」才走 `todos/complete`；点完清空按钮防重复 | TG 回调断言 + 幂等记录 | 通过 |
| AC-13 | 取消提醒 | 调 `/admin/reminders/cancel` | 写成功**且响应码正确**，不留孤儿提醒 | `mcp-test.mjs` 的 reminders 写类回合 | **25/27 FAILED**：n8n 2.37.7 把裸 `status` 当 HTTP 状态码 ⇒ 已知未修（RSK-01） |
| AC-14 | 请求跑满工具轮 | 收口 | 追加 `BUDGET_NOTE` system 消息（含"不要向用户提及预算"护栏） | A/B：有无提示各跑同一道信息不足题 | 已实现但**效果未证实**：两边都承认信息不足（707 vs 547 字），且那轮测的其实是坏掉的搜索后端 |

## 5. 五道门：现值、口径与它们的失败模式

| 门 | 命令 | 2026-10-30 实跑 | 口径与陷阱 |
| --- | --- | --- | --- |
| 工作流静态校验 | `node n8n/scripts/validate-workflows.mjs` | `validated 24 workflow file(s)` / `0 warning(s)` / EXIT=0 | 纯静态，不打印路径数；"39 条唯一 webhook 路径"要自己解析 `nodes[].parameters.path` |
| 冒烟 | `node --env-file=.env n8n/scripts/smoke-test.mjs` | **71/71，0 FAIL，0 SKIP**，EXIT=0 | **不是只读**：retention 组真删数据；happy-path 与托管 key 组真打 DeepSeek 花钱；PASS 分支不打印删了多少行 |
| MCP 回归 | `node --env-file=.env n8n/scripts/mcp-test.mjs` | **25/27 FAILED** | 2 条失败与 AC-13 同源 |
| Agent 评估 | `node --env-file=.env n8n/scripts/agent-eval.mjs` | **5/12 FAILED** | 7 条失败 = 沙箱通道没开（`EVAL_SANDBOX_URL` ECONNREFUSED），不是安全策略生效；另 1 条是模型抖动 |
| 自检 | 控制台一键 / `POST /webhook/admin/selfcheck/run` | 48 项 | 手动与定时**分开统计**，否则一次手动就把定时停摆盖住 |

报数的三条纪律（我自己犯过的错）：

1. 报 N 的正确办法是**数日志里的 PASS 行**，不是数代码里的 `check()` 站点。我曾静态数出"上限约 74"，实跑 71 —— 高估 3，因为 3 个站点在互斥分支里。
2. 数字必须带 **SKIP 状态与容器健康**。三处条件 SKIP（`N8N_API_KEY` / `DASHSCOPE_API_KEY` / 控制台可达）这次全命中，所以 71 是"满员形状"的数；换机器会低于 71。
3. **门本身的失败模式仍是缺陷**：栈没起来时第一条 `GET /healthz` 的 fetch 没有 try/catch ⇒ unhandled rejection、EXIT=1、**一行计数都不打**，"系统死了"读起来像"脚本坏了"而不是 0/71。这条我列进路线图 R-01，不做完我不说"CI 可靠"。
