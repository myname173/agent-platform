## 1. 问题定义

个人与小团队把 AI 用在真实工作上时，卡在四件事上，而这四件事**没有任何一个现成入口同时解决**：

| # | 痛点 | 现状 | 不解决的后果 |
| --- | --- | --- | --- |
| P1 | 对话产品不会真的"做事" | 聊天框只能生成文本，工具与流程各在一处 | 用户拿到一段建议，还得自己去执行 |
| P2 | 自己的资料进不了模型上下文 | 文档散在本地/IM/网盘 | 回答与私人业务无关，或靠复制粘贴，泄露且不可检索 |
| P3 | 推过来东西但收不回去 | 提醒/任务散在 IM 与日历，点了没反应 | 通知越多越没人看，闭环断裂 |
| P4 | **跑起来了但没人知道它坏了** | 定时任务静默停摆、搜索后端返回 200+空结果、绿灯时系统已死 | 用户第一次遇到就永久失去信任 |

P4 是这个项目真正的产品差异点。前三条是"做一个能干活的 Agent"，第四条是"**让它坏的时候会被发现**"。

> 一句话需求：**一个自己托管得住、能干成事、并且会自己喊疼的 AI Agent 中台。**

## 2. 目标与非目标

### 目标（v1，已达成，可当场复跑验证）

- G1 四个入口（LobeChat 前台 :3210 / 运营控制台 :3000 / Telegram 轮询桥 / 对外 MCP）**共用一套业务逻辑**，入口之间不互调。
- G2 模型能自主调用服务端工具完成任务，**工具错误以结构化信息回流**让模型可恢复，而不是整轮失败。
- G3 私域文档可自助摄取与检索，**文件不上传服务器**（浏览器端解析）。
- G4 推送可就地操作（回执 / 完成 / 顺延 / 取消），写回与面板同一行数据。
- G5 平台会自检：48 项覆盖基础设施 / 网关 golden / 流式 / 通道 / 数据新鲜度，失败自动推送，备份有心跳。
- G6 成本与错误率**看得见且会报警**，且看到的数与报警用的数是同一份。

### 非目标（刻意不做，写清楚免得被当成漏做）

- 不做多租户 SaaS、不做计费、不做用户体系（登录用 Clerk，仅护住控制台）。
- 不在控制台改阈值/密钥：`Settings` 页**只读**，改法只有 `.env` + `docker compose up -d n8n`。多一个可写入口就多一个真值来源。
- 不给模型改装流程的权力：L2 自建流程工具只有**点火权**（触发），不建 / 不改 / 不删。
- 不在 TLS / OAuth 就位前把 MCP 暴露公网（当前仅局域网）。
- 不追"更聪明的模型"：模型是 DeepSeek / DashScope 直连，我做的不是模型层。

## 3. 用户与场景

真实规模：**单机自托管 + 一个机主**。下面三个角色里，R2/R3 是"已实现但未形成多人日常使用"，我不把它说成多人在线协作。

| 角色 | 描述 | 高频场景 | 入口 | 关键诉求 |
| --- | --- | --- | --- | --- |
| R1 机主（我自己） | 一个人管全套系统，AI 是他的执行层 | 说一句就登记待办 / 派活；早上看晨报；出问题收告警；周日看周报 | TG + 控制台 + 前台 | 不用打开五个系统；坏的时候要知道 |
| R2 被派发的同事 | 只在 IM 里收到任务，不需要账号 | 收到「我收到了 / 已完成」两个按钮，点一下就写回 | TG（纯消息 + 内联按钮） | 零学习成本；不催第二次 |
| R3 外部 Agent 客户端 | 别的 AI 客户端 / 脚本把本平台当工具后端 | `tools/list` → `tools/call`，带 key、限速、留审计 | MCP :端口仅内网 | 稳定的契约，越权要被拦住 |

三个场景细节都落到实现上，不是概念：

- **R1 派发闭环**：`todo_add` 落库 → 负责人有通道就发本人，无通道**回落机主并标 degraded**（正文追加"（注：X 没有可用通道，已改投机主）"）→ 24h 未回执催办（`kind=待办催办`）→ 第 3 次升级机主（`kind=逾期升级`，`escalated=1`）→ 之后 `>2` 不再动。
- **R2 的按钮语义分离**：`ta 我收到了` 只写 `todos.ack_at`（**停催不关单**），`td 已完成` 才走 `/admin/todos/complete`。点完 `editMessageReplyMarkup` 清空按钮防重复；非机主只能操作派给自己的行。
- **R3 的治理**：每次 `tools/call` 写 `admin_audit`（含客户端信息 / 参数摘要 / 耗时 / 结果）；限流 60 次/分/密钥可覆盖；每工具级超时（常规 15s / 长任务 90s）。

## 4. 功能清单与优先级

优先级不打假分数。依据只有三类真实证据：**是否在必经路径上**、**有没有踩过的坑位编号**、**有没有会静默失败的通道**。M=S必须 / S=应该 / C=可以 / W=不做。

| 优先级 | 功能 | 状态（可核对） | 打分依据 |
| --- | --- | --- | --- |
| M | 工具型对话循环（服务端工具面 = 侧车 `SERVER_TOOLS` 16 个静态 + 动态 `wf_*`；≤2 轮，错误结构化回流） | 已实现，smoke 覆盖 | 所有入口的必经路径 |
| M | RAG 摄取与检索（pgvector + HNSW，1024 维 DashScope 嵌入） | 已实现；`kb-eval` 记录 hit@5 1.0 / MRR 0.903 | 私人资料进不了模型就没有业务相关性 |
| M | 待办 / 提醒 / 派发（含升级阶梯与无通道回落） | 已实现；**提醒接口在 n8n 2.37.7 下写成功却回 500（未修）** | 闭环的中枢；缺陷单独进风险册 RSK-01 |
| M | 幂等：显式 `X-Idempotency-Key` + 隐式 `session+tool+sha256(args)`（窗口 300s） | 已实现；`idempotency_records` 台账 | 没有它，一次超时重试就变成两条待办 |
| M | 自检 + 备份心跳（48 项，>30h 警告 / >40h 或失败不通过，失败推 TG） | 已实现 | G5 的直接兑现；坑位 9 |
| M | 错误率 / 成本 / 嵌入额度三类告警 + 冷却与升级不受去重 | 已实现 | 坑位 8、成本通路 |
| M | 登录与上游错误语义（401 不伪装成"用户未登录"，n8n 拒绝 → 502 + 一句人话） | 已实现 `frontent/src/lib/api-guard.ts:17-40` | 分不清是谁坏了，用户就只会反复重登 |
| M | 控制台 13 页 + 27 条 api route 代理（`N8N_API_KEY` 只在服务端） | 已实现 | R1 的主界面 |
| S | 对外 MCP（17 工具，限速 / 哈希 key 可独立吊销 / 审计） | 已实现；`mcp-test` 现值 **25/27 FAILED** | 契约已稳定，2 条失败与 RSK-01 同源 |
| S | 出向 MCP（`mcp_list_tools` / `mcp_call`，服务器须人登记） | 已实现 | 从"叶子"变"节点"；模型不可自注册 |
| S | 沙箱 `run_python` + 一次性审批（绑定 `sha256(代码原文)`） | 已实现；`agent-eval` **5/12 FAILED（沙箱通道未开）** | 提示词注入的硬边界是容器 + rlimits，静态扫描只是减速带 |
| S | 流式（stream-bridge 侧车）+ 双向语音 + 图片视觉 | 已实现（>900 字降级文字、>8MB 图片直接失败） | 体验门槛；降级路径都在 |
| S | 定时任务多时间点 + 每日一次守卫（fail-open，标记只在一轮成功后写） | 已实现 | 坑位 9：桌面机器凌晨不在线 |
| S | 文档生成 docforge（纪要 → 行动项 / 摘要归档 / 导出与签名链接） | 已实现 | R1 的高频产出 |
| S | 记忆（LobeHub 自动提取 + TG 保守提取，双库**单向**互通） | 已实现；控制台只读 | 跨会话稳定事实 |
| C | 知识库异步摄取（worker 队列） | **开关默认关**：`PLATFORM_KB_ASYNC_ENABLED=false`，`platform-worker` 在 `phase2` profile | 大文档量才需要，单机不急 |
| C | Prometheus 指标（`observability` profile，只采侧车 /metrics） | 已就位未常开 | 业务指标刻意**不重复定义**，避免两个"总量" |
| C | 事件总线 / outbox（`event-bus` profile + Kafka，写模式默认 `off`） | 试验 | 单节点受控部署下无收益 |

## 5. 关键约束（不写约束的 PRD 都是许愿）

- **一台 Windows 桌面 + Docker Desktop**：栈可能整段不在线，所以"挂在凌晨的定时任务"默认不可信（坑位 9）。这条直接催生了"多时间点 + 守卫"的设计。
- **无出站邮件**：n8n owner 的密码重置邮件永远收不到，恢复必须走库内 reset-token。运维文档按这条写，不写"去收邮件"。
- **嵌入额度 1M tokens/模型**：换嵌入模型需全量重嵌，两模型向量空间不通用。
- **上游牌价会变**：`cost_usd` 依赖 chat-gateway 里 `Prep Success Log` 节点的 PRICING 表；牌价调了不改，成本就与真实花费脱钩。
- **SearXNG 引擎会被封**：会出现 HTTP 200 + 空结果。已换成免 key 且实测可用的引擎集（yep / yandex / bing / sogou / quark / 360search / wikipedia）。
- **Postgres 只在容器网络内**（宿主不映射 5432）；`platform-runtime`、`kafka`、`prometheus` 只绑 `127.0.0.1`。
- **现网与仓库已漂移**：deploy 会覆盖现网改动（RSK-03）。

## 6. 编排层选型：为什么是 n8n

先说清楚性质：**这是一次需求匹配判断，不是我对竞品做了对照实验。** Dify / Coze / LangGraph / fastGPT 我没有在同一台机器上跑同题对比，所以这里不写"性能优于"。

| 判据 | 我的需求 | n8n 的对应 | 风险（我踩到的） |
| --- | --- | --- | --- |
| 逻辑单点收敛 | 四个入口不互调 | Webhook 即端点：39 条唯一路径、24 条工作流 | 工作流 JSON 与现网漂移，deploy 会覆盖 |
| 非工程角色可改 | 我自己也要能快速改流程 | 可视化画布 + Code 节点 | Code 节点里 SQL 占位符一列一用，否则 runner 直接死（坑位 1） |
| 数据落在自己手里 | 自托管、单机、可备份 | 主存储 Postgres + Data Table | Data Table ≠ 同名 PG 表；rows API 顺序与 250 上限有坑（坑位 3/10） |
| 可观测 | 失败要被发现 | 执行记录 + 我自己写的自检/告警层 | n8n 把响应里的裸 `status` 当 HTTP 状态码 → 提醒 500（RSK-01） |
| 权限边界 | 模型只能点火 | 触发式 webhook；建/改/删不给模型 | 契约需我自己守：工具定义曾有四份副本、其中两份是错的而四道门全绿（坑位 7） |

**如果重来一次我还会选 n8n 的理由只有两条**：入口收敛这一条架构决定能被他原生表达（webhook = 端点），以及"流程可视化 = 我能在评审时把逻辑直接摊给人看"。其余收益都可以用代码换。这条判断写下来，是为了面试被问"你为什么不用 X"时，我能承认代价，而不是背一套选型话术。
