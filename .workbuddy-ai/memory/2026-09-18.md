## 19:00 · B5 告警分级与静默期（提交 a535ae2）—— 顺带挖出「告警其实是瞎的」

### 交付
- `ops_alerts.severity`（info/warn/critical）；error_rate ≥0.8 → critical，配额 ≥95% → critical。
- `ops_alert_silence` 维护窗口：**窗口内照常记录、只跳过投递**——**静默绝不意味着失忆**。`mode=silence` + set/clear/list，**运行时可设、不需重启**。
- 自检 +1 → **40 项**。

### ⚠️ 最重要的发现：错误率告警一直是瞎的
为了造出真实告警（验证静默门），我注入了 32 个失败请求。结果窗口内明明 **40 次请求 34 次失败（85%）**，检查却报 **total=25 / errors=0**。三个原因叠加：
1. **rows API 的 `sortBy` 只有冒号百分号编码才生效**（`createdAt%3Adesc`），否则**最旧的在前**；
2. 循环假设「最新在前」，遇到窗口外第一行就 `break` → 几乎立刻退出；
3. `session_id='unknown'` 被当探针跳过，但**没带会话头的真实请求也记 'unknown'** → 真实错误被一起丢掉。

修法：**不依赖返回顺序**（break→continue，扫描全部），**只排除 `selfcheck`**。
修复后同一个场景报 **total=89 / errors=68 → alert_fired=true, severity=warn, delivery="silenced:maintenance"**。

### 教训
**「为了测试而故意制造故障」是发现隐藏 bug 的最有效手段之一**。如果不是为了验证静默门去注入失败请求，这个缺陷会一直躺着——告警平时不响，谁也不会怀疑它是坏的。
**一个从不响的告警比没有告警更危险**（同今天的 lobechat 探测：一个有时能过的检查比没有检查更危险）。
